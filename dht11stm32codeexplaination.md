# DHT11 Interfacing with STM32F401CCU6 — Code Explanation

## 1. Introduction

This document explains the Embedded C program used to interface the DHT11 temperature and humidity sensor with the STM32F401CCU6 Black Pill development board.

The program uses the STM32 Hardware Abstraction Layer (HAL) library and the Cortex-M4 Data Watchpoint and Trace (DWT) cycle counter to communicate with the sensor.

The DHT11 sends temperature and relative humidity measurements through a single digital DATA line connected to GPIO pin PA1.

### Main objectives

- Configure GPIO PA1 for sensor communication.
- Generate the DHT11 start signal.
- Receive temperature and humidity data.
- Decode the 40-bit data frame.
- Verify the received data using a checksum.
- Store the measurements and communication status in global variables.

## 2. Header Files

```c
#include "main.h"
#include <stdint.h>
```

- `main.h` contains STM32 HAL definitions, GPIO configuration types, and project-specific function declarations.
- `stdint.h` provides fixed-width integer types such as `uint8_t` and `uint32_t`.

These types help represent sensor data and processor cycle counts with known bit widths.

## 3. DHT11 Pin Configuration

```c
#define DHT_PORT GPIOA
#define DHT_PIN GPIO_PIN_1
```

These macros specify the microcontroller pin connected to the DHT11 DATA terminal.

- `GPIOA` selects GPIO port A.
- `GPIO_PIN_1` selects pin PA1.

Using macros makes the program easier to modify if the sensor is connected to a different pin.

### Hardware connections

| DHT11 pin | STM32F401CCU6 |
|---|---|
| VCC | 3.3 V |
| DATA | PA1 |
| GND | GND |

An appropriate pull-up resistor is required on the DATA line if the sensor module does not already include one.

## 4. Global Variables

```c
volatile uint8_t Temperature = 0;
volatile uint8_t Humidity = 0;
volatile uint8_t DHT_Status = 0;
```

### Temperature

Stores the integer temperature value received from the sensor, generally in degrees Celsius.

### Humidity

Stores the integer relative humidity value received from the sensor, expressed as a percentage.

### DHT_Status

Indicates the result of the most recent measurement attempt.

| Value | Meaning |
|---|---|
| 0 | No successful reading yet |
| 1 | Successful reading |
| 2 | Communication error |
| 3 | Checksum error |

The `volatile` keyword tells the compiler that the variables may change outside the normal flow it can infer. It is useful when inspecting values in the debugger.

However, `volatile` does not provide thread safety or synchronization by itself.

## 5. Microsecond Delay Using DWT

### Function: `delay_us()`

The DHT11 protocol contains pulses lasting only a few tens of microseconds. The standard HAL delay function, `HAL_Delay()`, operates in milliseconds and is therefore not suitable for measuring these short pulses.

The Cortex-M4 processor includes a DWT cycle counter called `CYCCNT`. It counts processor clock cycles.

The function uses the difference between two cycle-counter readings to create a delay.

### How it works

1. Read the current cycle count.
2. Calculate the number of cycles corresponding to the required delay.
3. Continuously check the cycle counter.
4. Exit the loop when the required number of cycles has elapsed.

For example, at an HCLK frequency of 84 MHz, approximately 84 processor clock cycles correspond to one microsecond.

The function assumes that the DWT cycle counter has already been enabled.

## 6. DWT Initialization

### Function: `DWT_Init()`

The DWT cycle counter must be enabled before it can be used for timing.

The function performs three operations:

1. Enables the Cortex-M trace functionality using the `TRCENA` bit in `CoreDebug->DEMCR`.
2. Resets the cycle counter by writing zero to `DWT->CYCCNT`.
3. Enables cycle counting using `DWT_CTRL_CYCCNTENA_Msk`.

After initialization, the program can use `DWT->CYCCNT` to measure elapsed processor cycles.

## 7. GPIO Configuration

The DHT11 DATA pin must support two operations: sending the start signal and receiving the sensor response.

### 7.1 Output configuration — `DHT_Output()`

This function configures PA1 as an open-drain output.

Open-drain operation allows the STM32 to pull the DATA line LOW or release it so that the pull-up resistor brings it HIGH.

The GPIO configuration includes:

- Pin: PA1
- Mode: Open-drain output
- Pull configuration: No internal pull-up or pull-down
- Output speed: Low

An external pull-up is assumed.

### 7.2 Input configuration — `DHT_Input()`

After sending the start signal, the STM32 must read the response and data generated by the DHT11.

This function configures PA1 as a digital input so the program can detect HIGH and LOW logic levels.

The program changes between output and input configurations as required by the communication sequence.

## 8. Waiting for a GPIO Logic Level

### Function: `Wait_Pin()`

The DHT11 communicates through changes in the DATA line's logic level.

This function waits until PA1 reaches a requested state.

Its parameters are:

- `state`: the required logic level, either HIGH or LOW.
- `timeout_us`: the maximum waiting time in microseconds.

### Operation

1. Record the starting cycle count.
2. Convert the timeout into processor clock cycles.
3. Read PA1 repeatedly until the requested logic level appears.
4. If the timeout expires, return `0`.
5. If the requested level is detected, return `1`.

The timeout prevents the program from waiting indefinitely when the sensor is disconnected or communication fails.

## 9. Reading One Byte

### Function: `Read_Byte()`

The DHT11 sends data one bit at a time, with the most significant bit first.

Each data bit begins with a LOW interval followed by a HIGH pulse. The duration of the HIGH pulse identifies whether the bit represents binary 0 or binary 1.

### Bit decoding

- A shorter HIGH pulse represents binary 0.
- A longer HIGH pulse represents binary 1.

The program uses a threshold of approximately 45 microseconds to distinguish the two bit values.

### Operation

1. Wait for PA1 to become HIGH.
2. Record the cycle counter at the start of the HIGH pulse.
3. Wait for PA1 to become LOW.
4. Calculate the elapsed cycles.
5. Compare the pulse duration against the threshold.
6. Shift the previously received bits left by one position.
7. Set the least-significant bit to 1 if the pulse is longer than the threshold.
8. Repeat until all eight bits have been received.

Finally, the reconstructed byte is written through the pointer provided to the function.

If a pulse transition is not detected within the allowed timeout, the function returns `0` to indicate a communication error.

## 10. Reading the Complete DHT11 Frame

### Function: `DHT_Read()`

The DHT11 transmits a total of 40 bits, arranged into five bytes.

| Array index | Data |
|---|---|
| `data[0]` | Integer relative humidity |
| `data[1]` | Decimal relative humidity |
| `data[2]` | Integer temperature |
| `data[3]` | Decimal temperature |
| `data[4]` | Checksum |

### 10.1 Sending the start signal

The program configures PA1 as an output and pulls it LOW for 20 milliseconds.

This signals the DHT11 that the microcontroller wants a measurement.

After the delay, the program releases the line and changes PA1 to input mode so it can receive the sensor response.

### 10.2 Detecting the sensor response

The program checks for the expected response sequence:

1. LOW
2. HIGH
3. LOW

These transitions indicate that the sensor has begun responding and is preparing to transmit its data.

If any expected transition is not detected before the timeout, the function returns a communication error.

### 10.3 Receiving the 40-bit frame

The program calls `Read_Byte()` five times.

Each call receives eight bits, giving a total of:

40 bits = 5 bytes × 8 bits per byte.

The five received bytes are stored in the `data` array.

### 10.4 Checksum verification

The checksum is calculated by adding the first four bytes:

```c
uint8_t sum = (uint8_t)(
    data[0] + data[1] + data[2] + data[3]
);
```

The cast to `uint8_t` retains the lowest eight bits of the sum.

The calculated checksum is compared with the fifth byte received from the sensor.

- If both values match, the frame passes the checksum check.
- If the values differ, the function returns `2` to indicate a checksum error.

The checksum helps detect certain transmission errors, but it does not guarantee that every possible corrupted frame will be detected.

### 10.5 Extracting the measurements

After checksum verification:

```c
*hum = data[0];
*temp = data[2];
```

The pointer `hum` receives the integer relative humidity, while `temp` receives the integer temperature.

The program does not use the decimal bytes. Typical DHT11 readings use zero decimal bytes, and the implementation is designed for integer measurements.

The function returns `1` when communication and checksum verification succeed.

## 11. Main Function

The `main()` function initializes the microcontroller and repeatedly requests measurements from the sensor.

### 11.1 HAL initialization

```c
HAL_Init();
```

Initializes the STM32 HAL and its time base, which is used by functions such as `HAL_Delay()`.

### 11.2 System clock configuration

```c
SystemClock_Config();
```

Configures the processor and system clocks. This function is normally generated by STM32CubeMX.

The configured clock frequency is important because the DWT timing calculations depend on the actual HCLK frequency.

### 11.3 GPIO initialization

```c
MX_GPIO_Init();
```

Initializes the GPIO peripherals configured in the CubeMX project.

The DHT11 functions subsequently configure PA1 as an output or input as needed.

### 11.4 DWT initialization

```c
DWT_Init();
```

Enables the cycle counter required for microsecond timing.

### 11.5 Main application loop

Inside `while (1)`, the program repeatedly performs the following operations:

1. Creates temporary variables for temperature and humidity.
2. Calls `DHT_Read()` to request a sensor reading.
3. Checks the returned status.
4. Updates the global variables if the reading succeeds.
5. Records an error status if communication or checksum verification fails.
6. Waits approximately one second before the next attempt.

### Handling the return value

| Return value from `DHT_Read()` | Action in `main()` | `DHT_Status` |
|---|---|---|
| `1` | Update temperature and humidity | `1` |
| `0` | Record communication failure | `2` |
| `2` | Record checksum failure | `3` |

If a measurement fails, the program retains the previous values of `Temperature` and `Humidity`. Therefore, the status variable should be checked before treating those values as a new measurement.

## 12. Complete Program Flow

The complete program follows this sequence:

1. Initialize HAL.
2. Configure the system clock.
3. Initialize GPIO.
4. Enable the DWT cycle counter.
5. Configure PA1 as an output and release the DATA line.
6. Pull DATA LOW for 20 ms to start communication.
7. Switch PA1 to input mode.
8. Detect the DHT11 response.
9. Receive five bytes using pulse-duration decoding.
10. Verify the checksum.
11. Extract temperature and humidity.
12. Update the global variables and status.
13. Wait one second.
14. Repeat the process.

## 13. Important Implementation Considerations

- **Pull-up resistor:** Ensure that the DATA line has a suitable pull-up resistor if one is not already present on the module.
- **Timing accuracy:** Interrupts and software overhead can affect pulse measurement. A hardware-timer input-capture implementation may provide more reliable timing.
- **Clock configuration:** Verify the HCLK frequency because the microsecond timing calculations depend on it.
- **Reading interval:** Allow at least one second between DHT11 measurement requests.
- **Data validity:** Check `DHT_Status` before using the latest temperature and humidity values.
- **Decimal values:** This implementation reads only the integer temperature and humidity bytes.
- **Error handling:** A timeout or checksum mismatch indicates that the current measurement should not be accepted.

## 14. Conclusion

This project demonstrates digital sensor interfacing using the STM32 HAL library. It combines GPIO configuration, cycle-counter timing, pulse-width decoding, checksum verification, and global-variable updates to obtain temperature and relative humidity readings from the DHT11 sensor.

The implementation also demonstrates how timeouts and status variables can be used to identify communication failures and invalid data.
